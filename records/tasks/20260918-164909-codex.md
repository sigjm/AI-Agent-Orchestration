# 누끼를 GPU에서 돌리도록 onnxruntime-gpu 전환

- 워커: codex
- 발행: 2026-09-18 16:49:09
- 지휘: Claude Code (오케스트레이터 세션)

## 지시

[구현 과제] rembg 누끼를 L40S GPU 에서 돌린다

## 배경 — 내가 사내 서버에서 실측한 사실 (재측정 불필요)

우리 이미지의 onnxruntime 에 CUDA 프로바이더가 없다.

```
['AzureExecutionProvider', 'CPUExecutionProvider']
```

그래서 GPU 노드를 써도 누끼는 CPU 로 돈다. 500x500 입력 한 장 기준 실측:

| | 시간 | 피크 RSS |
| --- | --- | --- |
| rembg 세션 로드 | 21.3초 | 2.19 GB |
| 누끼 1장 | 28.5초 | 9.26 GB |

배포 대상은 `g6e.xlarge` = **4 vCPU / 32 GiB / L40S 1장**. 지금 구조는 GPU 값을
내면서 4 vCPU 로 배경 제거를 한다. 사내 서버(8코어)에서는 렌더 도중 컨테이너가
OOMKilled(exit 137) 로 죽었다.

## 할 일

**EKS 배포 이미지는 `deploy/sglang/Dockerfile` 이고 베이스가
`lmsysorg/sglang:v0.5.19` (CUDA) 다.** 여기서 누끼가 CUDA 를 쓰게 한다.

1. `deploy/sglang/Dockerfile` 에서 `onnxruntime-gpu` 를 설치한다.
   - **베이스 이미지의 CUDA/cuDNN 버전을 먼저 확인하고** 그에 맞는 onnxruntime-gpu
     버전을 고를 것. 아무 버전이나 넣지 마라.
   - CPU 휠(`onnxruntime`)과 같이 깔리면 충돌한다. 이 이미지에서만 CPU 휠을 걷어내고
     GPU 휠을 넣어라.
   - `pyproject.toml` 의 `onnxruntime==1.29.0` 은 **건드리지 마라.** Mac 개발과 CI,
     그리고 CPU 전용 `deploy/Dockerfile` 이 그걸 쓴다.

2. 코드에서 세션 생성 시 CUDA 프로바이더를 우선 쓰고, 없으면 CPU 로 떨어지게 한다.
   `src/detail_page_ai/source_photos.py` 의 `new_session` 호출부(약 499~516행)를 보라.
   - **CPU 환경에서 반드시 그대로 동작해야 한다.** Mac, CI, `deploy/Dockerfile`,
     GPU 없는 사내 서버 전부 지금과 같이 돌아야 한다.
   - 사용 가능한 프로바이더가 무엇이었는지 로그로 한 줄 남겨라. 나중에 GPU 에서
     실제로 CUDA 를 탔는지 확인할 근거가 필요하다.

## 검증에 대해 — 솔직하게

**우리에게 GPU 가 없다.** 사내 서버도 Mac 도 CUDA 가 없다. 그러니
"GPU 에서 빨라졌다"는 검증은 이번에 불가능하다. 지어내지 마라.

할 수 있는 검증만 하라.
- `deploy/sglang/Dockerfile` 이 빌드되는지 (베이스가 크니 오래 걸린다. 빌드가
  불가능하면 불가능하다고 보고하라)
- 빌드된 이미지에서 `onnxruntime.get_available_providers()` 에
  `CUDAExecutionProvider` 가 들어 있는지
- CPU 환경에서 기존 동작이 그대로인지 (전체 pytest)

빌드를 못 했으면 "빌드하지 않았다" 고 그대로 적어라. 우리 문서에는 미빌드 항목을
숨기지 않는 원칙이 있다.

## 테스트

CPU 폴백을 검증하는 테스트를 추가하라. 프로바이더 목록에 CUDA 가 없을 때
세션 생성이 실패하지 않고 CPU 로 진행되는지 확인하는 것이다.
단언을 약하게 만들지 마라. 전체 pytest 를 돌리고 숫자를 그대로 보고하라.
현재 기준은 409 passed 다.

## 결과

### 변경 파일

- `deploy/sglang/Dockerfile`: `uv sync`가 설치한 CPU `onnxruntime`을 EKS 전용 venv에서 제거하고 `onnxruntime-gpu==1.29.0`을 설치하도록 추가했습니다. `pyproject.toml`의 CPU 의존성은 변경하지 않았습니다.
- `src/detail_page_ai/source_photos.py`: 사용 가능한 ONNX Runtime 프로바이더를 한 줄 로그로 남기고, CUDA가 있으면 `CUDAExecutionProvider`를 우선 사용하며 없으면 `CPUExecutionProvider`로 폴백하도록 세션 생성 경로를 변경했습니다.
- `tests/test_source_photos.py`: CUDA 미사용 CPU 폴백과 CUDA 우선 선택을 검증하는 테스트를 추가했습니다.

### 버전 근거

- 베이스 이미지 `lmsysorg/sglang:v0.5.19`를 로컬에서 검사한 결과 `CUDA_VERSION=13.0.3`, `NV_CUDNN_PACKAGE=libcudnn9-cuda-13=9.14.0.64-1`, PyTorch `2.13.0+cu130`이었습니다.
- 따라서 CUDA 13.0/cuDNN 9.x 조합을 지원하는 `onnxruntime-gpu==1.29.0`을 선택했습니다. ONNX Runtime 공식 CUDA Execution Provider 호환성 표도 1.29.x를 CUDA 13.0 및 cuDNN 9.x 조합으로 안내합니다: <https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html>

### 검증

- 집중 테스트: `2 passed in 0.14s`
- 전체 테스트: `411 passed, 2 warnings in 14.22s`
- 로컬 CPU 환경의 `onnxruntime==1.29.0` 프로바이더: `['CoreMLExecutionProvider', 'AzureExecutionProvider', 'CPUExecutionProvider']` — CUDA 없음.
- Docker 빌드 중 `uv pip uninstall ... onnxruntime` 및 `uv pip install ... onnxruntime-gpu==1.29.0` 단계는 성공했습니다.
- `deploy/sglang/Dockerfile` 전체 빌드는 기존 Node/npm 조립 단계에서 실패했습니다: `/usr/local/bin/npm`이 요구하는 `../lib/cli.js`를 찾지 못해 `npm ci`에서 `Cannot find module '../lib/cli.js'`가 발생했습니다. 따라서 완성된 이미지에서 `get_available_providers()`를 실행할 수 없었고 CUDA 프로바이더 포함 여부도 확인하지 못했습니다.
- GPU 장비가 없는 환경이므로 실제 GPU 실행 속도 향상은 검증하지 않았습니다.
- `git diff --check`: 통과.

### 미해결 이슈

- Docker 이미지의 기존 Node/npm 복사 경로(`/usr/local/bin/npm` symlink와 `/usr/local/lib/node_modules/npm` 복사 조합)가 전체 빌드를 막고 있습니다. 이번 과제에서는 범위를 넓혀 Node 설정을 수정하지 않았습니다.
- 완성 이미지의 ONNX Runtime 프로바이더 확인과 실제 L40S 실행 검증은 위 빌드 차단 이슈 및 GPU 부재로 남아 있습니다.
