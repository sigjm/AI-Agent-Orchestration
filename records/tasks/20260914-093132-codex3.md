## 지시

추론 서버를 SGLang 으로 옮기기 위한 클라이언트 작업입니다. 관리자 결정: Ubuntu g6e.xlarge(NVIDIA L40S 48GB 1장)에서 텍스트(Qwen3.8-27B)와 이미지(FLUX.2-klein-9B)를 모두 SGLang 으로 서빙한다. `sglang serve` 는 프로세스당 모델 하나이므로 SGLang 프로세스 2개(텍스트용·이미지용)를 같은 GPU 에 띄운다.

브랜치 `deploy/ubuntu` 에서 작업하세요(체크아웃돼 있음). 커밋하지 마세요.

## 담당 범위

## 1. 먼저 SGLang HTTP 계약을 소스로 확인 (추측 금지)
네트워크가 됩니다. SGLang 저장소(github.com/sgl-project/sglang)의 **실제 소스**와 공식 문서로 확인하세요. 블로그 요약만으로 판단하지 마세요.
- **텍스트:** `/v1/chat/completions` 가 우리 요청을 받는지 — 메시지 content 에 `{"type":"image_url","image_url":{"url":"data:image/...;base64,..."}}`, `response_format: {"type":"json_object"}`. 현재 요청 형식은 `clients.py` 의 `MlxServeChatClient.generate_json`(123행~).
- **이미지 생성:** SGLang Diffusion 의 `/v1/images/generations` 요청 필드(`size`, `response_format: b64_json`, steps 에 해당하는 필드명 등)와 응답 형태. 현재 형식은 `MlxServeImageClient.generate`(190행~).
- **이미지 편집(원본 참고):** 현재 우리는 MLX Serve 전용으로 `/v1/images/generations` 에 `mode: "edit"`, `image`(base64), `steps`, `strength` 를 JSON 으로 보냅니다(`MlxServeImageClient.edit`, 214행~). SGLang 이 FLUX.2-klein 편집 입력을 **어떤 엔드포인트·어떤 형식**(예: `/v1/images/edits` multipart, 또는 JSON 의 image 필드)으로 받는지 소스에서 찾으세요. FLUX.2-klein 에서 steps·guidance·strength 에 해당하는 인자가 무엇이고 무시되는 것이 무엇인지도.
확인한 근거(파일 경로·줄, 문서 URL)를 보고에 붙이세요. 확인이 안 되는 것은 "확인 필요"로 남기세요.

## 2. `sglang` provider 추가
- `LOCAL_TEXT_PROVIDER` 에 `sglang`, `LOCAL_IMAGE_PROVIDER` 에 `sglang` 값을 추가합니다. `config.py` 의 Literal, `factory.py` 의 분기·오류 메시지를 함께. `BACKGROUND_PROVIDER` 가 `mlx` 이미지 provider 를 요구하는 제약(`factory.py` 93행 부근)도 `sglang` 에서 성립하게.
- 텍스트: SGLang 이 1절에서 확인한 대로 우리 요청을 그대로 받으면 **기존 OpenAI 호환 클라이언트를 재사용**하세요(새 클래스 불필요). 차이가 있으면 최소 수정.
- 이미지: 1절 계약에 맞는 클라이언트를 만드세요(`generate`, `edit` 두 메서드, 반환은 이미지 bytes — 기존 `MlxServeImageClient` 와 같은 인터페이스라 호출부는 그대로). **MLX 경로는 그대로 두세요** — 로컬 Mac 개발은 계속 MLX 를 씁니다.
- 환경변수 계약(배포 파일 담당 워커가 이 값으로 씁니다 — 바꾸지 마세요): `LOCAL_TEXT_PROVIDER=sglang`, `LOCAL_TEXT_URL=http://sglang-text:30000`, `LOCAL_IMAGE_PROVIDER=sglang`, `LOCAL_IMAGE_URL=http://sglang-image:30001`. 모델 ID 는 기존 `LOCAL_TEXT_MODEL`, `LOCAL_IMAGE_MODEL` 로 받습니다.

## 검증

- `.venv/bin/python -m pytest -q` 전수 통과(현재 349).
- 실서버에서만 확인 가능한 항목은 목록으로 따로 보고하세요(첫 배포 체크리스트에 들어갑니다).

## 결과

- 구현한 변경:
  - `src/local_detail_page_ai/clients.py:56-89`에 dependency-free multipart JSON 응답 transport를 추가하고, `:298-402`에 `SglangImageClient`를 추가했습니다. `generate()`는 `POST /v1/images/generations`에 `model`, `prompt`, `negative_prompt`, `n`, `size`, `response_format=b64_json`, `num_inference_steps`를 JSON으로 보내고, 선택적으로 `guidance_scale`·`seed`를 전달합니다. `edit()`은 `POST /v1/images/edits`에 `image` 파일과 같은 공통 필드를 multipart form으로 보내며 `data[0].b64_json`을 bytes로 디코드합니다.
  - 기존 `MlxServeChatClient`를 SGLang 텍스트 provider에서 그대로 재사용했습니다. MLX 이미지 요청 경로와 payload는 유지했고, 이미지 기본 모델은 상업 운영 가능한 `black-forest-labs/FLUX.2-klein-4B`로 맞췄습니다. 모델 ID에 따른 분기는 넣지 않았습니다.
  - `src/local_detail_page_ai/factory.py:41-114`에 `sglang` 텍스트·이미지 provider를 연결하고, `BACKGROUND_PROVIDER=sglang`을 `LOCAL_IMAGE_PROVIDER=sglang`과 함께 사용하도록 했습니다. 이미지 생성이 켜진 경우 두 provider 값이 일치하지 않으면 시작 시 실패합니다.
  - `src/detail_page_ai/config.py:22-50`의 세 provider Literal에 `sglang`을 허용하고 이미지 모델 기본값을 4B로 바꿨습니다. 배포 env의 `LOCAL_TEXT_MODEL`·`LOCAL_IMAGE_MODEL` 값은 그대로 `model` 필드에 전달됩니다.

- 확인한 SGLang 계약과 근거:

  - 공식 Diffusion API 문서 [`openai_api.md`](https://docs.sglang.io/docs/sglang-diffusion/api/openai_api.md)와 [SGLang 공식 문서 원본](https://github.com/sgl-project/sgl-docs/blob/main/docs/sglang-diffusion/api/openai-api.mdx)의 246-278행은 생성 `POST /v1/images/generations`의 JSON과 `b64_json` 응답, 편집 `POST /v1/images/edits`의 multipart `image` 입력을 명시합니다.

  - `.venv/bin/python -m compileall -q src tests` 및 `git diff --check` 통과.
  - `.env.example`를 실제 settings 입력으로 읽는 확인 결과 `sglang qwen-text sglang flux-klein sglang`으로 파싱되었습니다.
  - stubbed `urlopen`을 사용한 `UrllibJsonTransport.post_multipart` smoke test에서 multipart header, `image` filename/content type, endpoint, JSON 응답 파싱을 확인했습니다.
  - 최종 전수 실행: `352 passed, 1 failed` (총 353개). 유일한 실패는 `tests/test_security.py::test_env_example_contains_placeholders_not_credentials`이며, 다른 워커의 기존 `.env.example` 변경으로 `LOCAL_TEXT_MODEL=qwen-text`가 되어 기존 MLX 모델 기대값과 충돌한 것입니다. 금지된 `.env.example`는 수정하지 않았습니다. 해당 테스트를 제외한 전수 실행은 `352 passed, 1 deselected`입니다.
  - 커밋하지 않았습니다.

- 첫 배포에서 실서버로 확인할 체크리스트:
  1. g6e.xlarge의 한 L40S에서 텍스트 SGLang을 `30000`, 이미지 Diffusion SGLang을 `30001`에 각각 기동하고 두 health endpoint가 응답하는지 확인합니다.
  2. 텍스트 `--served-model-name`과 `LOCAL_TEXT_MODEL`, 이미지 `--served-model-name`과 `LOCAL_IMAGE_MODEL`이 각각 정확히 같은지 확인합니다. 클라이언트는 model ID를 변환하지 않습니다.
  3. 텍스트 `/v1/chat/completions`에 data URI 이미지와 `response_format={"type":"json_object"}`를 보내 Qwen 응답이 JSON object로 파싱되는지 확인합니다.
  4. 이미지 `/v1/images/generations`에 `size`, `n=1`, `response_format=b64_json`, `num_inference_steps`를 보내 base64 결과와 실제 해상도를 확인합니다.
  5. 이미지 `/v1/images/edits`에 `-F image=@...` multipart 요청을 보내 원본 입력이 처리되고 base64 결과가 오는지 확인합니다. `guidance_scale`·`seed` 동작과 `strength` 미전송이 FLUX.2-klein-4B에서 의도한 품질을 내는지 별도로 확인합니다.
  6. 두 프로세스 동시 기동·반복 생성 시 L40S VRAM, startup time, latency, concurrency를 측정하고 상업 운영에는 4B 모델과 라이선스가 사용되는지 확인합니다.

- 미해결 이슈:
  - GPU와 SGLang 서버가 없는 환경이라 실제 Qwen 멀티모달 응답, FLUX.2-klein-4B 생성·편집, model name 일치, VRAM/성능은 확인하지 못했습니다.
  - 공식 handler가 `guidance_scale`·`seed`를 받는 것은 확인했지만 FLUX.2-klein-4B에서의 guidance 의미와 실제 품질, `strength`를 대체할 모델별 제어 방식은 실서버 품질 테스트가 필요합니다. `strength`는 현재 구현에서 의도적으로 요청에 넣지 않았습니다.
  - 전수 테스트의 `.env.example` 불일치는 다른 워커 변경과 기존 보안 테스트의 기대값을 조정해야 해결되며, 담당 범위 밖 파일이라 보존했습니다.
