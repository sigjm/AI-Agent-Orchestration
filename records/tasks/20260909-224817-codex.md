## 지시

## 문제 (실측으로 확정)

`/v1/images/edits` (multipart) 경로에서 우리가 보내는 **`steps` 와 `strength` 가 둘 다
서버에 반영되지 않는다.** 통제 실험으로 확인했다.

실험 산출물: `generated/experiments/image-steps-ab-20260909-223049/`
(`results.json` 에 요청값·서버 로그값·소요시간이 전부 기록돼 있다. 먼저 읽어라.)

**Phase 1 — 파라미터 이름 확인 (`/v1/images/generations`, JSON 경로)**

| 보낸 필드명 | 값 | 서버 로그 | 소요 |
|---|---|---|---|
| `steps` | 8 | **8** | 39.3s |
| `num_inference_steps` | 8 | 4 | 18.8s |
| `num_steps` | 8 | 4 | 18.3s |
| `n_steps` | 8 | 4 | 19.1s |

**이름은 `steps` 가 맞고, JSON 경로에서는 정상 반영된다.** 8스텝이 4스텝의 약 2배 시간이 걸린 것으로 실제 실행도 확인된다.

**Phase 2 — 실제 사용 경로 (`/v1/images/edits`, multipart)**

steps 4/8/16 × strength 0.25/0.50/0.75 아홉 조합을 돌렸더니

- 요청 steps 8·16 이 **전부 로그에 `steps=4`** 로 찍혔다
- 소요시간이 28~32초로 **전 셀 동일**
- 아홉 장의 **SHA-256 이 전부 동일** (`e1b213380ced…`) — 바이트 단위로 같은 이미지다

즉 이 경로에서는 steps 도 strength 도 결과에 아무 영향이 없다.

## 왜 중요한가

상세페이지의 **모든 이미지 생성이 `/v1/images/edits` 를 탄다** (원본을 참조로 넣는
in-context edit). 즉 `strength` 는 원본 보존과 장면 자연스러움을 조절한다고 코드가 믿고 있는
값인데 **실제로는 아무 일도 하지 않는다.** 이 손잡이를 살리기 전에는 이미지 품질 실험이
의미를 갖지 못한다.

## 유력한 원인

`src/local_detail_page_ai/clients.py` 의 두 경로가 값을 다른 타입으로 보낸다.

- 259행 (JSON, `/v1/images/generations`): `"steps": self.steps` — **정수**
- 295행 (multipart, `/v1/images/edits`): `"steps": str(self.steps)`, `"strength": f"{strength:.2f}"` — **문자열**

서버가 multipart 폼 필드의 문자열을 숫자로 파싱하지 못하고 기본값으로 떨어지는 것으로 보인다.
다만 **이건 가설이다. 실측으로 확인하고 고쳐라.**

## 작업

1. multipart 경로에서 `steps` 와 `strength` 가 실제로 반영되는 형식을 찾아라.
   확인 방법은 실험과 같다. 요청을 보낸 뒤 `.local/mlx-serve/mlx-serve.log` 의
   `[image] generating ... steps=N` 값을 읽으면 서버가 무엇으로 실행했는지 나온다.
   `strength` 는 로그에 안 찍히므로, **같은 프롬프트·같은 참조 이미지로 strength 만 바꿔
   두 장을 만들고 SHA-256 이 달라지는지**로 확인하라. 같으면 여전히 무시되는 것이다.
2. 원인이 확인되면 `src/local_detail_page_ai/clients.py` 를 고친다.
3. multipart 로는 끝내 반영이 안 된다면, edit 요청을 JSON 경로로 보낼 수 있는지
   확인해 보고, 그것도 안 되면 **"서버가 지원하지 않는다"는 결론과 근거를 보고에 적어라.**
   억지로 고친 척하지 마라. 안 되는 것을 확인한 것도 결과다.
4. 테스트를 추가한다 — 요청 페이로드에 두 값이 **서버가 받아들이는 형식으로** 실린다는 것을
   검증하는 단위 테스트. 기존 테스트 방식(`tests/test_local_llm.py` 의 transport 스텁)을 따르라.

## 결과

### 원인 확인

- `generated/experiments/image-steps-ab-20260909-223049/results.json`을 먼저 읽고 기존 결과의 SHA-256을 재확인했다.
- 수정 전 multipart 실측은 요청 `steps=4/8/16` 모두 서버 로그 `steps=4`였고, 9개 결과가 모두 `e1b213380ceda0c545bb24e1dac0d4cb5bfc385f4958751bf71b2de163dbd617`로 동일했다.
- 기존 실험의 `steps=4` 소요시간은 29.996~31.797초, `steps=8`은 29.356~31.692초로 차이가 없었다.
- 설치된 MLX Core 26.9.1 구현을 확인한 결과 multipart `/v1/images/edits`는 내부 `mode:"edit"` JSON으로 변환하면서 `steps`와 `strength`를 전달하지 않는다. JSON 이미지 경로는 숫자형 `steps`와 `strength`를 파싱하지만, FLUX.2 in-context `mode:"edit"`에서는 `strength`를 의도적으로 사용하지 않는다.

### 변경 파일

- `src/local_detail_page_ai/clients.py`
  - `MlxServeImageClient.edit()`를 multipart `/v1/images/edits` 대신 JSON `/v1/images/generations`의 `mode:"edit"` 경로로 전환했다.
  - 참조 이미지를 base64로 보내고 `steps`는 정수, `strength`는 실수로 전송하도록 했다.
  - 더 이상 사용하지 않는 로컬 이미지용 multipart transport 구현과 주입을 제거했다.
- `tests/test_local_llm.py`
  - 이미지 편집 관련 스텁을 JSON transport로 전환했다.
  - `mode`, base64 `image`, 숫자형 `steps`·`strength` 페이로드 회귀 테스트를 추가했다.

### 수정 후 실측

- 동일 프롬프트·참조 이미지로 JSON edit을 순차 실행했다(총 3장).
- `steps=4, strength=0.25`: 서버 로그 `steps=4`, 34.184초, SHA-256 `e1b213380ceda0c545bb24e1dac0d4cb5bfc385f4958751bf71b2de163dbd617`
- `steps=8, strength=0.25`: 서버 로그 `steps=8`, 83.888초, SHA-256 `9c1ec01d2aa47fffa39a56e6f712bacb51df0c61e9bbd1860cfb8a0c9be80a11`
- `steps=4, strength=0.75`: 서버 로그 `steps=4`, 58.586초, SHA-256 `e1b213380ceda0c545bb24e1dac0d4cb5bfc385f4958751bf71b2de163dbd617`
- 따라서 `steps`는 수정 후 실제 반영됐고, 동일 `steps=4`에서 `strength=0.25/0.75`는 여전히 동일 결과여서 현재 edit 모드에서는 반영되지 않음이 확인됐다.

### 미해결 이슈

- 현재 모델의 in-context `mode:"edit"`는 서버 설계상 `strength`를 무시한다. `strength`가 필요한 경우 서버가 image-to-image variation을 지원하는 모델과 `mode:"variation"` 경로가 필요하며, 현재 FLUX.2 모델에서는 그 경로가 지원되지 않는다. 따라서 `strength`를 반영한다고 가장하지 않고, JSON 숫자형 전송과 서버 한계를 함께 기록했다.
