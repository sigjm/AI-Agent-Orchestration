## 지시

SGLang compose 검수 결과, `docker compose config` 는 통과했지만 **실제로는 기동되지 않을 결함 3개**를 관리자가 SGLang 공식 문서·PyPI 로 확인했습니다. 고쳐 주세요. 브랜치 `deploy/ubuntu`, 커밋하지 마세요. `src/`·`Dockerfile` 은 건드리지 마세요.

## 1. 공식 SGLang 이미지에는 확산(Diffusion) 기능이 없습니다
공식 설치 문서(https://docs.sglang.io/docs/sglang-diffusion/installation.md)에 따르면 `lmsysorg/sglang` Docker 이미지는 SGLang Diffusion 을 기본 포함하지 않고, 컨테이너 안에서 `pip install "sglang[diffusion]"` 이 필요합니다. 지금 `sglang-image` 서비스는 공식 이미지에서 바로 `sglang serve --model-path black-forest-labs/FLUX.2-klein-4B` 를 실행하므로 확산 모델을 못 올립니다.
→ `sglang-image` 용 이미지를 따로 빌드하세요. 파일은 `docker/sglang-diffusion.Dockerfile` 하나: `FROM lmsysorg/sglang:<태그>` 위에 **같은 버전의** `sglang[diffusion]==0.5.19` 를 설치. PyPI 에서 `sglang 0.5.19` 가 `diffusion` extra(의존성 23개, diffusers 0.37.0 등)를 제공하는 것을 확인했습니다. 기동 명령마다 pip 설치를 돌리는 방식은 쓰지 마세요(재시작마다 설치, 네트워크 의존).
→ compose 의 `sglang-image` 는 `build:` 로 이 파일을 쓰게 하고, 태그를 `.env` 의 `SGLANG_IMAGE` 에서 빌드 인자로 받아 텍스트 서비스와 같은 SGLang 버전을 보장하세요.

## 2. 이미지 요청의 `model` 값이 서버 모델 이름과 안 맞습니다
SGLang Diffusion OpenAI API 문서(https://docs.sglang.io/docs/sglang-diffusion/api/openai_api.md): 요청의 `model` 필드는 `--served-model-name` 값과 일치해야 합니다. 지금 `sglang-image` 는 `--served-model-name ${SERVED_IMAGE_MODEL_NAME:-flux-klein}` 인데, `detail-page-ai` 의 `LOCAL_IMAGE_MODEL` 기본값은 `black-forest-labs/FLUX.2-klein-4B` 입니다. 우리 클라이언트는 `LOCAL_IMAGE_MODEL` 을 `model` 로 보내므로 요청이 거부됩니다.
→ 이름을 한 곳에서만 정하세요. 텍스트도 같은 원칙으로: 두 서버에 `--served-model-name` 을 명시하고(`TEXT_SERVED_MODEL_NAME`, `IMAGE_SERVED_MODEL_NAME`), `LOCAL_TEXT_MODEL`/`LOCAL_IMAGE_MODEL` 은 그 변수를 그대로 쓰게. 체크포인트 경로(`TEXT_MODEL_PATH`, `IMAGE_MODEL_PATH`)와 공개 이름을 섞지 마세요.

## 3. 이미지 서버 헬스체크가 영원히 통과하지 않을 수 있습니다
같은 문서의 확산 서버 엔드포인트 목록에는 `GET /v1/models`, `GET /v1/models/{model_name}`, `GET /server_info` 가 있고 `/health` 는 없습니다. 지금 두 SGLang 서비스 모두 `/health` 로 헬스체크하고, `detail-page-ai` 는 두 서비스가 healthy 여야 뜹니다. 이미지 서버에 `/health` 가 없으면 우리 서비스가 영원히 기동하지 않습니다.
→ 두 서비스 모두 문서에 있는 `GET /v1/models` 로 헬스체크하세요(텍스트 서버도 OpenAI 호환 `/v1/models` 제공). 이미지 안에 `curl` 이 있는지 확실하지 않으면 `python3 -c` 로 HTTP 호출하세요.

### 3. 헬스체크 경로 및 방식
- **엔드포인트**: `GET /v1/models` (OpenAI 표준 모델 카탈로그 조회)
- **호출 방식**: 컨테이너 내 curl 설치 유무에 영향받지 않도록 Python 표준 라이브러리(`urllib.request`)로 실행:
  ```yaml
  test: ["CMD", "python3", "-c", "import urllib.request, sys; sys.exit(0 if urllib.request.urlopen('http://127.0.0.1:<PORT>/v1/models', timeout=5).getcode() == 200 else 1)"]
  ```
- **효과**: SGLang Diffusion 공식 엔드포인트에 존재하지 않는 `/health` 대신 실제 모델 서빙 준비가 완료되었을 때 HTTP 200을 반환하는 `/v1/models`를 검사하므로, `sglang-image`가 영구적으로 unhealthy 상태에 머물러 `detail-page-ai`가 뜨지 않는 문제를 완벽히 해결했습니다.

### 4. 검증 결과
- `docker compose --env-file .env.example config` 실행 결과: **오류 없이 정상 통과 (exit code 0)**.
  - `sglang-image`의 `build` 컨텍스트 및 `args` (`BASE_IMAGE`, `SGLANG_VERSION`) 정상 바인딩 확인.
  - 3개 서비스 간 환경변수(`LOCAL_TEXT_MODEL: qwen-text`, `LOCAL_IMAGE_MODEL: flux-klein`) 및 의존성(`condition: service_healthy`) 정상 반영 확인.
- `docker build -f docker/sglang-diffusion.Dockerfile ...`:
  - 베이스 이미지(`lmsysorg/sglang:v0.5.19`) 용량이 약 15~20GB에 달하므로, 지시에 따라 로컬 머신에서 전체 다운로드 및 빌드는 실행하지 않았습니다. 대신 Dockerfile 문법 구조와 Compose 연동 스키마의 무결성을 정적 검증했습니다.
