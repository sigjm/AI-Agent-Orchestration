## 배경 (실측)

`src/local_detail_page_ai/clients.py` 는 이미지 요청에 `steps` 를 실어 보내고 기본값이 **12** 다
(`steps: int = 12`, 230행). 그런데 모델 서버 로그(`.local/mlx-serve/mlx-serve.log`)에 남은
이미지 생성 **65회가 전부 `steps=4`** 다. 호출부 어디에서도 4로 덮어쓰지 않는다.
즉 우리가 보내는 `steps` 필드가 서버에 반영되지 않고 있다.

두 가지를 실측으로 밝혀야 한다.
1. 서버가 받아들이는 스텝 파라미터 이름이 무엇인가, 혹은 아예 고정인가
2. 스텝과 edit 강도(strength)를 바꾸면 결과가 실제로 달라지는가

이미지 모델은 `mlx-community/flux2-klein-9b-4bit` 이고, Klein 은 증류된 few-step 변형이라
스텝을 올려도 좋아진다는 보장이 없다. **가설을 검증하는 것이지 개선을 전제하지 마라.**

## Phase 1 — 파라미터 이름 확인 (생성 4회)

`/v1/images/generations` 에 짧은 프롬프트로 4회 요청한다. 매 요청마다 스텝 필드 이름만 바꾼다.

- `steps`, `num_inference_steps`, `num_steps`, `n_steps` — 값은 전부 **8** 로 보낸다

각 요청 직후 `tail -5 .local/mlx-serve/mlx-serve.log` 에서 `steps=N` 값을 읽어 기록한다.
`steps=8` 이 찍히는 이름이 있으면 그것이 정답이다. 넷 다 `steps=4` 면 **서버가 증류 모델
스케줄로 고정하는 것**이므로 그렇게 결론 내고 Phase 2 의 steps 축을 생략한다.

## Phase 2 — 격자 생성

실제 사용 경로는 `/v1/images/edits` (원본을 참조로 넣는 in-context edit)다. 이 경로로 격자를 만든다.

- 참조 이미지: `data/evaluation/cma_real_v1/images/cma-122443.jpg` (청자 병) 한 장 고정
- 프롬프트: 모든 셀에 **동일한 문자열**을 쓴다. 파이프라인이 실제로 쓰는 것과 비슷하게,
  제품이 놓일 실내 장면을 묘사하는 한국어/영어 프롬프트 하나를 정해 `results.json` 에 그대로 기록하라
- 축:
  - steps: Phase 1 에서 파라미터가 먹히면 `4 / 8 / 16`, 안 먹히면 이 축 생략
  - strength: `0.25 / 0.50 / 0.75`
- 즉 최대 9장, 최소 3장. **그 이상 생성하지 마라.** GPU 시간이 비싸다.

### 4. 보고 항목 (사실 기반 요약)

#### (1) 스텝 파라미터가 반영되는가, 반영된다면 이름은 무엇인가
- `/v1/images/generations` 경로에서는 **`steps`** 라는 이름으로 정상 반영됩니다 (8 스텝 요청 시 서버 로그에 `steps=8` 기록, 소요 시간 18.8s -> 39.3s로 2.1배 증가).
- 그러나 실제 상세페이지 파이프라인에서 참조 이미지를 넣어 호출하는 **/v1/images/edits 경로에서는 `steps` 파라미터가 서버에서 완전히 무시되며 전건 `steps=4`로 고정**됩니다.
  - 서버 로그: `[image] edit: reference 581x893 -> 576x864 (in-context conditioning)` 직후 모든 요청에서 `[image] generating 1024x1024 steps=4`만 기록됨.
  - 클라이언트(`src/local_detail_page_ai/clients.py`)가 기본값 12를 보내더라도 서버 로그 65건이 전부 4였던 원인이 바로 이 때문입니다.
