## 지시

## 인프라팀이 원하는 구조
```
L40S  └ ai-sglang  └ FastAPI :8000 + SGLang
T4    └ ai-ollama  └ FastAPI :8000 + Ollama
```
워크로드마다 **백엔드가 호출할 FastAPI :8000 을 그 컨테이너가 직접 제공**해야 합니다.

## sglang/Dockerfile — 한 컨테이너에 FastAPI + SGLang 2개
관리자 판단: 우리 파이프라인은 SGLang 서버가 **둘**(텍스트·비전 30000, 이미지 확산 30001)입니다. 쿠버네티스 device plugin 은 GPU 를 컨테이너 단위로 배타 할당하므로 멀티컨테이너로 쪼개면 L40S 한 장을 나눠 쓸 수 없습니다. 따라서 한 컨테이너에서 세 프로세스(uvicorn + SGLang 텍스트 + SGLang 이미지)를 띄웁니다.
- 베이스: `lmsysorg/sglang:v0.5.19`(CUDA 포함). 그 위에 `sglang[diffusion]==0.5.19`, `bitsandbytes==0.50.2`, 그리고 우리 서비스 런타임(`uv sync --locked --no-dev`, Node.js, Playwright Chromium)을 설치.
- 우리 서비스 실행 방식은 루트 `Dockerfile` 과 같게: `/app/src` 소스 실행(`PYTHONPATH=/app/src`)이라 `PROJECT_ROOT=/app` 이 유지되고 `web/`, `assets/references/detail-page-layouts.json`, `scripts/runtime/render_detail_page.mjs` 를 복사해야 합니다. 이 자산이 빠지면 렌더가 깨지고 레이아웃 카탈로그가 조용히 빈 리스트가 됩니다.
- `entrypoint.sh`: SGLang 텍스트·이미지 서버를 백그라운드로 띄우고 uvicorn(`serve-ai`)을 포그라운드로. 어느 프로세스든 죽으면 컨테이너가 종료되게(프로세스 감시 후 exit). **로그는 전부 stdout/stderr 로** — 파일로 빼지 마세요.
- 두 SGLang 인자는 정본과 `docker-compose.yml` 을 그대로 따르되 host 는 `127.0.0.1`(같은 컨테이너 내부 통신).
- 서비스 환경변수 기본값: `LOCAL_TEXT_PROVIDER=sglang`, `LOCAL_IMAGE_PROVIDER=sglang`, `BACKGROUND_PROVIDER=sglang`, `LOCAL_TEXT_URL=http://127.0.0.1:30000`, `LOCAL_IMAGE_URL=http://127.0.0.1:30001`, `LOCAL_TEXT_MODEL=qwen-text`, `LOCAL_IMAGE_MODEL=flux-klein`.

## ollama/Dockerfile — 한 컨테이너에 FastAPI + Ollama
- 베이스: `ollama/ollama` 공식 이미지(태그 고정) 또는 CUDA 베이스에 Ollama 설치. 어느 쪽을 골랐는지와 이유를 주석에.
- 우리 서비스는 `LOCAL_TEXT_PROVIDER=ollama`(`src/local_detail_page_ai/clients.py` 의 `OllamaChatClient`, 기본 포트 11434)로 붙습니다.
- **이미지 생성은 이 워크로드에서 불가능합니다.** Ollama 는 확산 모델을 서빙하지 않습니다. 따라서 `LOCAL_IMAGE_PROVIDER=none`, `BACKGROUND_PROVIDER=none` 을 기본값으로 두세요(팩토리 제약상 두 값이 맞아야 합니다 — `factory.py` 확인).
- 모델은 이미지에 굽지 말고 **런타임에 받도록** 하고(`OLLAMA_MODELS` 경로를 마운트 가능한 위치로), 어떤 모델을 쓸지는 `LOCAL_TEXT_MODEL` 환경변수로 받게 하세요. T4 는 16GB 라 27B 급은 들어가지 않습니다 — 기본값은 12B 급 비전 모델(예: 코드 기본값 `gemma3:12b`)로 두고, 선택은 운영 결정 사항으로 주석에 남기세요.
- `entrypoint.sh`: `ollama serve` 를 백그라운드, uvicorn 포그라운드. 로그 stdout/stderr.

## 두 이미지 공통 운영 기준 (인프라팀 요구)
- `CMD`/`ENTRYPOINT` 정의, FastAPI `:8000` 노출(`EXPOSE 8000`).
- **Secret 을 이미지에 굽지 말 것.** `HF_TOKEN`, `BACKEND_AUTH_TOKEN`, `AI_INTERNAL_AUTH_TOKEN` 등은 런타임 주입.
- **컨테이너 내부에 영구 데이터를 쓰지 말 것.** 우리 서비스는 SQLite(`SQLITE_PATH`)와 asset store(`ASSET_STORE_DIR`), 모델 캐시(`HF_HOME`, `U2NET_HOME`, `OLLAMA_MODELS`)를 씁니다. 이 경로들을 **전부 마운트 가능한 한 곳**(예: `/var/lib/detail-page-ai`, 모델은 `/models`)으로 모으고 `VOLUME` 선언 대신 기본값만 지정하세요. 어디에 무엇이 쌓이는지 Dockerfile 주석에 명시하세요.
- 비루트 실행(UID/GID 10001). 베이스 이미지가 root 전제라면 필요한 디렉터리 소유권을 넘기고 `USER` 로 전환하세요. 전환이 불가능한 지점이 있으면 그 이유를 주석에 남기고 보고하세요.
- `linux/amd64` 빌드 가능해야 합니다.
- `HEALTHCHECK` 는 `GET /health` 200 으로(쿠버네티스는 무시하지만 로컬 검증용). 루트 `Dockerfile` 의 기존 404 방식도 `/health` 로 바꾸세요.

## 결과

### 변경 파일

- `sglang/Dockerfile`: FastAPI + SGLang 텍스트/이미지 서버를 한 컨테이너에서 실행하도록 작성했습니다.
- `sglang/entrypoint.sh`: 텍스트 서버와 이미지 서버를 백그라운드로 시작하고 `serve-ai`를 foreground/PID 1로 실행합니다. 어느 SGLang 프로세스든 종료되면 API와 나머지 서버도 종료합니다. 로그 리다이렉트는 없습니다.
- 루트 `Dockerfile`: 허용된 변경으로 `HEALTHCHECK` 대상만 기존 404 경로에서 `GET /health` 200으로 변경했습니다.
- 관리자 결정에 따라 `ollama/Dockerfile`, `ollama/entrypoint.sh`는 만들지 않았고 삭제할 파일도 없었습니다. `src/`, `docker/sglang-diffusion.Dockerfile`, `docker-compose.yml`, `.env.example`은 변경하지 않았습니다.

### 베이스/운영 처리

- 주 베이스는 `lmsysorg/sglang:v0.5.19`입니다. CUDA와 SGLang 텍스트 런타임을 그대로 사용하고 `sglang[diffusion]==0.5.19`, `bitsandbytes==0.50.2`를 추가 설치합니다.
- `node:22-bookworm-slim`의 Node 22 런타임을 복사했습니다. 잠금된 Playwright 1.62가 Node.js 20 이상을 요구하므로 CUDA 이미지의 배포판 Node 버전에 의존하지 않게 했습니다.
- 프로젝트는 `/app/src` + `PYTHONPATH=/app/src`로 실행하며 `web/`, `assets/references/detail-page-layouts.json`, `scripts/runtime/render_detail_page.mjs`를 복사합니다. 프로젝트 venv는 `uv sync --locked --no-dev --no-install-project --no-cache --python 3.13`으로 만들고, SGLang은 베이스 이미지 Python 인터프리터를 보존한 `/usr/local/bin/sglang-python`으로 실행합니다.
- `appuser` UID/GID 10001을 만들고 `USER appuser`로 전환했습니다. `/app`, Playwright, `/var/lib/detail-page-ai`를 appuser 소유로 설정했습니다.
- `HF_TOKEN`, `BACKEND_AUTH_TOKEN`, `AI_INTERNAL_AUTH_TOKEN`을 이미지에 설정하지 않았습니다.

### 단일 PVC 경로

EKS에서 `/var/lib/detail-page-ai` 하나만 마운트하는 전제로 다음 경로를 모두 그 아래에 모았습니다. Dockerfile에는 `VOLUME`을 선언하지 않았습니다.

- SQLite: `/var/lib/detail-page-ai/state.sqlite3`
- assets: `/var/lib/detail-page-ai/assets`
- Hugging Face 텍스트/이미지 모델: `/var/lib/detail-page-ai/models/huggingface`
- rembg/U2NET: `/var/lib/detail-page-ai/models/u2net`
- Torch 모델 캐시: `/var/lib/detail-page-ai/models/torch`
- XDG/SGLang/FlashInfer/Triton/TorchInductor/CUDA 캐시: `/var/lib/detail-page-ai/cache` 하위

빈 PVC로 경로가 가려지는 경우를 위해 entrypoint가 모델·캐시 경로를 `mkdir -p`로 초기화합니다. SQLite 부모 디렉터리와 asset store의 `objects`/`metadata`는 각각 `persistence.py`와 `assets.py`가 이미 생성합니다. PVC가 UID 10001에 쓰기 가능하도록 EKS `fsGroup` 또는 동등한 볼륨 권한 설정은 필요합니다.

### 검증

- `bash -n sglang/entrypoint.sh`: 통과.
- Dockerfile 정적 점검: `VOLUME` 없음, Docker COPY 원본 존재, `EXPOSE 8000`, `/health` 헬스체크, `USER appuser`, 지정된 SGLang 인자와 단일 PVC 경로 확인 통과.
- 가짜 명령 프로세스 점검: 이미지 SGLang을 즉시 실패시키면 로그가 stdout/stderr로 나오고 entrypoint가 exit 137로 종료하며 텍스트 서버/API를 정리했습니다. foreground API에 TERM을 보내면 exit 0으로 종료했습니다. 빈 경로 초기화 디렉터리도 생성됐습니다.
- `docker version`: Docker CLI 29.6.2는 있으나 Docker Desktop API 소켓이 응답하지 않았습니다. Docker Desktop 기동 후 60초간 재확인했지만 서버가 올라오지 않았습니다.
- `docker buildx build --check --platform linux/amd64 -f sglang/Dockerfile .` 및 실제 `docker buildx build --platform linux/amd64 -f sglang/Dockerfile --progress=plain .`: 모두 Docker API 소켓 권한/데몬 부재로 이미지 pull·빌드 시작 전에 중단되었습니다. 따라서 실제 amd64 빌드, 패키지 설치, 모델 다운로드 및 GPU 동시 기동은 미검증입니다.

### 미해결 이슈

- Docker Desktop 데몬이 실행되지 않아 이미지 빌드는 수행하지 못했습니다.
- GPU에서 L40S 한 장에 텍스트·이미지 모델을 동시에 적재하는 동작은 로컬 GPU 부재 및 데몬 부재로 검증하지 못했습니다.
- 빈 PVC가 root 소유로 제공되는 클러스터에서는 위의 UID 10001 쓰기 권한 설정(`fsGroup` 등)이 배포 매니페스트에 반드시 포함되어야 합니다.
