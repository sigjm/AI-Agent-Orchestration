# Figma 프로토타입의 디자인 워크플로우대로 테스트 사이트 흐름 맞추기

> **목표 (사용자 보충 지시, 이 절이 아래 내용보다 우선):** "안에 있는 프로토타입처럼 이 서비스가 잘 돌아가게끔 할 것".
> 화면 모양을 흉내 내는 게 아니라, **프로토타입에 그려진 흐름 전체가 테스트 환경에서 실제로 끝까지 동작**하게 만드는 것이 목표다.
> - 프로토타입이 쇼핑몰 전체(탐색·상품·장바구니·주문·판매자 스튜디오·챗봇 등)를 다루면 그 흐름 전부가 대상이다. 아래 1절의 (라) "그 밖이면 멈춤" 규칙은 적용하지 않는다.
> - 우선순위: ① 판매자 AI 상세페이지 생성(입력 → 분석 → **초안 확인·승인** → 렌더 → 편집·게시 → 구매자 상품 화면 노출) ② 구매자 챗봇 ③ 프로토타입의 나머지 흐름.
> - 3절의 "기능이 없으면 흉내 내지 말 것"은 이렇게 바꾼다: 프로토타입 단계에 대응하는 기능이 없으면 **서버 테스트용 FE·BE 사본에 실제로 동작하게 최소 구현**한다(BE에 이미 있는 API, 예: 생성 초안 조회·승인 API는 FE에 연결). 새로 만든 것은 결과에 "신규 구현"으로 따로 표시한다. 여전히 동작하지 않는 가짜 버튼은 만들지 않는다.
> - 우리 AI 쪽(상세페이지 생성·콜백)에 문제가 있으면 우리 저장소에서 고친다(커밋 없이, 테스트 포함).

관리자(메인 Claude 세션) 지시다. 사용자 요청 원문: "여기있는 디자인 워크플로우 따르게끔 안에 수정좀 해줘 잘".

## 기준 디자인

- Figma 프로토타입 「삼성가고싶어요 프로토타입」
  `https://www.figma.com/<redacted>`
- 시작 노드 `273:9640`. Figma 연결(`figma.use_figma`)로 연다. **읽기만 하고 Figma 파일은 수정하지 않는다.**

## 할 일

### 1. 워크플로우 읽기 — 먼저 결과에 적는다

- 시작 노드부터 프로토타입 연결(클릭 → 이동)을 따라가며 화면 순서를 정리한다: 화면 이름 / 노드 id / 화면의 주요 요소·문구 / 다음 화면으로 가는 동작
- 각 화면 캡처를 남긴다
- 이 흐름이 **무엇에 대한 것인지** 판정한다
  - (가) 판매자 AI 상세페이지 생성 흐름(사진·정보 입력 → AI 분석 → 초안 확인·승인 → 렌더 결과 → 편집·게시 등)
  - (나) AI가 만드는 상세페이지 결과물 자체의 디자인(섹션 구성·색·타이포)
  - (다) 구매자 챗봇 흐름
  - (라) 그 밖 — 이 경우 수정하지 말고 판정 근거만 적고 멈춘다

### 2. 지금 구현과 비교

어제 띄운 Ubuntu 테스트 환경(`http://<ubuntu-server>:13300`, 서버 `~/midam-e2e`, 인계 내용은 `20261001-ubuntu-e2e.md`)을 실제 브라우저로 같은 순서대로 따라가며, 화면별로 **Figma와 다른 점**을 표로 만든다(빠진 화면·단계, 순서, 문구, 버튼, 상태 표시, 레이아웃).
어제 확인한 "판매자 화면에 초안 승인 단계가 연결돼 있지 않음"이 Figma 흐름의 어느 단계에 해당하는지도 적는다.

### 3. 수정

판정에 따라 수정할 곳이 다르다.

- (가)·(다): **서버 테스트용 사본만** 고친다 — FE `~/midam-e2e/frontend`, 필요하면 BE `~/midam-e2e/backend`. 실제 FE·BE 저장소(Jangingmall/frontend·backend)는 건드리지 않는다. 고친 내용은 FE·BE 팀에 전달할 수정안이 된다.
- (나): 우리 저장소의 상세페이지 생성 코드(템플릿·`react_document_builder.py` 등)를 고친다. 커밋은 하지 않는다. 기존 테스트가 깨지지 않게 하고, 바뀐 동작에는 테스트를 추가한다.
- Figma에 있지만 구현에 대응 기능(API 등)이 아예 없는 단계는 억지로 흉내 내지 말고 "기능 없음"으로 적는다. 화면만 있고 동작하지 않는 버튼을 만들지 않는다.

### 4. 검증

- 수정 후 같은 흐름을 실제 브라우저로 처음부터 끝까지 다시 진행한다(판매자는 `e2e-artisan@midam.test`, 구매자는 `e2e-user@midam.test`. 비밀번호는 서버 compose 설정 참고).
- 화면별로 Figma 캡처와 나란히 비교한 스크린샷을 남긴다.
- AI 생성이 필요한 단계는 어제처럼 Mac의 MLX(Qwen3.8-27B·flux2-klein-9b)를 쓴다. 모델을 바꾸지 않는다.

## 결과

- **상태: 권한 확보 전까지 보류.** Figma `use_figma`와 읽기 전용 `get_design_context` 모두 “파일 편집 권한이 없다”는 응답으로 노드 메타데이터를 제공하지 않았다. 사용자가 내일 편집 권한을 확보하겠다고 해 현재 Figma 흐름 추적은 여기서 건너뛴다. Figma 파일은 수정하지 않았다.
- Chrome 프로토타입에서 시작 노드 `273:9640`의 첫 화면이 쇼핑몰 홈임을 시각 확인했다. 상단 `전체 카테고리`를 열어 카테고리 메가 메뉴를 확인했고, 하위 항목 클릭으로 상품 목록 화면(표시된 노드 `54:67783`, `전체 카테고리 > 패션·액세서리 > 부채`)에 도달했다. 프로토타입 전체 흐름·스크린샷 저장·구현 비교는 권한 확보 후 진행해야 한다.
- Figma 흐름 단계가 확정되지 않아 이번 작업의 FE·BE·AI 기능 변경은 하지 않았다. 서버 테스트 FE 사본에는 별도 사용자 질문에 따라 PC 상단 오른쪽 프로필 아이콘 옆 로그아웃 버튼을 연결했다(`~/midam-e2e/frontend`의 `header.tsx`, `gnb.tsx`, `gnb.test.tsx`; 설명 주석도 갱신). 실제 FE·BE 저장소는 건드리지 않았다.
- 로그아웃 FE 회귀 테스트는 전체 230개 파일·1,441개 테스트 통과. Ubuntu의 테스트용 FE 컨테이너만 재빌드·재시작했다. 브라우저 로그인 검증은 테스트 사용자 로그인 화면에서 `접근 권한이 없어요`가 표시되어 로그아웃 클릭까지 진행하지 못했다.
- Git 상태를 변경하는 명령은 실행하지 않았다. Figma 작업에서 남은 일: 편집 권한 확보 후 시작 노드부터 전체 프로토타입을 다시 추적하고, 요구된 화면별 캡처·수정 전후 비교·Ubuntu 브라우저 검증을 진행한다.

### 2026-10-02 시연 안정화 보강

#### 조치

- Ubuntu 사내 테스트 스택(`~/midam-e2e`)에서 상세페이지 로드·갱신 경로를 보강했다. BE `ContentService`가 생성된 텍스트/표 콘텐츠를 상세 응답에 유지하고, FE `detail-mapper.ts`가 절대 이미지 URL을 처리하도록 했다. 상품 변경 웹훅은 태그뿐 아니라 홈·상품 목록·상품 상세 경로도 재검증한다.
- FE 홈의 API 모드에서 지원되지 않는 판매량·위시리스트 정렬이 목업 상품으로 대체되던 경로를 제거했다. 지원되는 최신순 API와 두 번째 페이지로 실제 샘플만 보여 주며, API 모드에서는 가짜 기획전 상품을 감춘다. 변경 경로: `frontend/src/app/page.tsx`, `frontend/src/lib/isr/revalidation.ts`, `frontend/src/app/api/revalidate/route.ts` 및 재검증 테스트.
- 판매자 AI 생성 초안의 실제 확인·승인 단계를 FE에 연결했다. 상품 정보·이미지 확인 체크 전에는 승인을 막고, 승인 뒤 BE 렌더 작업이 완료되면 편집기로 이어진다. 주요 화면: `frontend/src/app/seller/products/new/_components/ServerStudioDraftReview.tsx`.
- 챗봇 검색 동기화에서 상품 설명과 상세 콘텐츠를 지식 문맥으로 전달하고, 소재인 한지를 염색 방식으로 분류하던 코드를 바로잡았다. 출처 없는 세부 제작 공정·관리법은 사실처럼 답하지 않도록 검증했다. 주요 BE 경로: `backend/src/main/java/com/jangingmall/backend/content/application/ContentService.java`, `backend/src/main/java/com/jangingmall/backend/content/domain/AiCatalogCodes.java` 및 관련 테스트.
- 시연 카탈로그의 공개 상품을 출처·가격·사진을 확인한 실제 상품 7개로 정리했다. 공개 API의 전체 개수가 7이고 썸네일 7개 모두 HTTP 200임을 재확인했다. 현재 상품 상태는 `ON_SALE` 7개, `HIDDEN` 655개, `DRAFT` 70개다. Artisan 64에는 공개 7개와 새 AI 초안 1개만 있다. 과거 비공개 데이터는 삭제하지 않고 공개 목록에서 제외했다.
- 상품 732는 상품 731과 같은 전주합죽선의 별도 AI 시연 초안이다. 구매자 카탈로그에 중복 노출되지 않도록 `DRAFT`에 남겼다. 공식 판매처 공개 정보(대나무·한지, 54×29.5cm, 80g, 119,980원)를 기준으로 만들고, 확인되지 않은 제작 기간·공정은 제외했다. [공식 상품 출처](https://shopofkorea.com/goods/view?no=13724)

#### 검증 결과

- 홈과 상품 목록은 HTTP 200, 홈은 재검증 후 `HIT`; 홈 응답에 공개 7개가 표시되고 옛 목업 상품명은 없다. 공개 상품 API는 `totalElements=7`, 부채 상품 상세 API는 HTTP 200이다.
- 기존 판매 상품 731은 판매자 저장·새로고침·검수 요청·초안 승인·게시 후 구매자 상세 화면까지 브라우저 E2E 통과했다. 구매자 페이지 HTTP 200, 상세 이미지 11/11 로드 성공.
- 새 AI 생성 상품 732는 입력 → 분석 → `DRAFT_READY` → 검토 승인(HTTP 202) → 렌더 완료(8개 섹션·사진 8/8) → 편집·저장·새로고침까지 실제 브라우저에서 통과했다. 근거가 불명확한 AI 문구를 정리하고 미확인 placeholder가 없는 것을 재확인했다. 게시하지 않아 구매자 공개 상품 수는 유지된다.
- 챗봇은 네 차례 대화가 모두 HTTP 201이고 첫 답변이 상품 731을 추천 카드로 표시했다. 의도적으로 한 번 주입한 HTTP 503 오류에 `다시 시도` 버튼이 보였고 재시도는 HTTP 201로 복구됐다. 네트워크 요청 실패는 없었다. 첫 로그인 전 토큰 갱신의 HTTP 401은 로그인 후 200으로 회복되는 기존 인증 부트스트랩 동작이다.
- FE 재검증 테스트 5개 통과, 해당 FE 빌드 성공. 관련 기존 FE 전체 테스트 230개 파일·1,441개 테스트, BE 상세·AI 카탈로그 테스트도 통과한 기록을 확인했다. FE 테스트 컨테이너만 재빌드·재시작했으며 재기동 준비까지 약 37초 걸렸다. 서버 확인 시 FE·BE·챗봇·DB·스토리지와 기존 프록시 서비스는 실행 중이었다.
