# 텍스트 서버 준비 후 이미지 서버 기동 (Stage 기동 실패 수정)

## 지시

# 배경 — Stage L40S 에서 텍스트 서버가 기동 중 죽었다

`deploy/sglang/entrypoint.sh` 는 텍스트 서버(30000)와 이미지 서버(30001)를 **동시에** `&` 로 띄운다.
Stage 로그:

    'mem_fraction_static': 0.5
    Load weight begin. avail mem=43.46 GB
    Load weight end.  elapsed=252.71 s  avail mem=8.52 GB  mem usage=34.94 GB
    RuntimeError: Not enough GPU memory for hybrid (mamba/linear-attention) state cache.
    Computed max_mamba_cache_size=-45 (total_rest_memory=-13.32 GB, mamba_cache_per_req=146.81 MB)

SGLang 은 캐시 예산을 `rest = 지금 남은 VRAM − 기동 시점 VRAM × (1 − mem_fraction_static)` 로 잡는다.
텍스트 가중치는 19.57 GiB 인데 34.94 GB 가 빠졌다 — 텍스트가 252초 동안 로드하는 사이 **이미지 서버가
약 15.4 GB 를 가져갔고**, SGLang 은 그걸 텍스트 서버 몫의 여유에서 뺐다.

    동시 기동:  rest = 8.52 − 43.46×0.5 = −13.21 GB   (로그 −13.32, 재현됨)
    텍스트 단독: rest = (43.46−19.57) − 43.46×0.5 = +2.16 GB

즉 **동시 기동이 원인**이다. 이미지 서버는 텍스트 서버가 준비된 뒤에 띄워야 한다.

# 할 일 — `deploy/sglang/entrypoint.sh`

1. 텍스트 서버를 먼저 띄우고, `http://127.0.0.1:30000/v1/models` 가 200 을 줄 때 이미지 서버를 띄운다.
   `/v1/models` 는 `src/detail_page_ai/app.py` 의 `/health/ready` 가 쓰는 것과 같은 엔드포인트다.
   **curl 은 이미지에 있다는 보장이 없다.** `sglang-python -c` 로 urllib 을 써라.

2. **FastAPI(`exec serve-ai`) 를 늦추지 마라.** 지금처럼 즉시 떠서 `/health` 가 바로 200 을 줘야 한다
   (Kubernetes liveness). 대기와 이미지 기동은 **백그라운드 감시 쪽**에서 해라. `/health/ready` 는 두 서버가
   다 뜰 때까지 503 인 현재 동작 그대로다.

3. `TEXT_READY_TIMEOUT` (기본 1800초). 텍스트가 준비 전에 죽거나 시간을 넘기면 **이미지를 띄우지 말고**
   기존 실패 경로처럼 컨테이너를 멈춰라 (지금 `watch_processes` 가 main 을 KILL 하는 방식).

4. 이미지를 띄운 뒤의 감시 동작은 지금과 같다 — 둘 중 하나라도 죽으면 컨테이너를 멈춘다.

5. 텍스트 준비 직후, 이미지 준비 직후 각각 한 줄씩 VRAM 을 로그로 남겨라.
   `nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader` — nvidia-smi 가 없으면 조용히 건너뛴다.
   목적: Stage 가 뜰 때마다 "텍스트만 올라간 상태"와 "둘 다 올라간 상태"의 VRAM 이 기록되게 하려는 것.
   이미지 준비 여부도 `:30001/v1/models` 200 으로 본다. 이 대기 중 이미지나 텍스트가 죽으면 실패 경로.

6. `TEXT_MAX_RUNNING_REQUESTS` 가 **설정됐을 때만** `--max-running-requests N` 을 붙여라.
   기존 `TEXT_MEM_FRACTION`·`TEXT_CONTEXT_LENGTH` 와 같은 방식이다. 인프라가 동시 처리 수 조정을 요청했다.

7. `TEXT_MEM_FRACTION` 기본값 0.50 은 **바꾸지 마라.** 값은 GPU 실측으로 정한다.

# 테스트 — `tests/test_sglang_entrypoint.py`

기존 테스트는 DRY_RUN 만 본다. 순서를 확인하려면 **가짜 실행파일**을 tmp PATH 에 둬야 한다
(`sglang-python`, `sglang`, `serve-ai`, `nvidia-smi`). 각자 이벤트를 파일에 적게 해라.
`sglang-python` 은 서버 기동(`-m sglang.launch_server`)과 준비 확인(`-c ...`) 두 용도로 불리니
둘을 구분해서 처리해야 한다 (예: 가짜 텍스트 서버가 몇 초 뒤 마커 파일을 만들고, `-c` 는 그 파일로 판단).

최소 이 셋:
- API 가 이미지보다 먼저 뜨고, 이미지는 텍스트가 준비된 **뒤에만** 뜬다
- 텍스트가 준비 전에 죽으면 이미지는 **아예 안 뜨고** 컨테이너가 0 이 아닌 코드로 끝난다
- DRY_RUN 출력에 `--max-running-requests` 가 **설정했을 때만** 들어간다

## 결과

- 변경 파일은 지시대로 `deploy/sglang/entrypoint.sh`와 `tests/test_sglang_entrypoint.py` 두 개뿐이다. 커밋은 만들지 않았다.
- `TEXT_MAX_RUNNING_REQUESTS`가 설정된 경우에만 텍스트 SGLang 명령에 `--max-running-requests`를 추가하도록 했다. 미설정 시 DRY_RUN 출력에 해당 옵션이 없다.
- 텍스트 서버를 먼저 기동한 뒤, 백그라운드 supervisor가 `sglang-python -c`와 Python `urllib`로 `127.0.0.1:30000/v1/models`의 HTTP 200을 확인한다. 준비 전 텍스트 프로세스 종료 또는 `TEXT_READY_TIMEOUT`(기본 1800초) 초과 시 이미지를 기동하지 않고 기존처럼 main 프로세스를 KILL해 실패 종료한다.
- 텍스트 준비 직후 `nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader` 결과를 한 줄로 기록하고, 이미지 서버를 기동한 뒤 `127.0.0.1:30001/v1/models`가 200이 될 때까지 기다린 후 같은 방식으로 VRAM을 기록한다. `nvidia-smi`가 없거나 결과가 없으면 조용히 건너뛴다.
- FastAPI는 supervisor를 백그라운드로 시작한 직후 기존의 `exec serve-ai`를 실행하므로, 텍스트·이미지 준비 대기가 API 기동을 지연시키지 않는다. 가짜 실행파일 테스트에서 `api-start`가 `image-start`보다 먼저 기록되는 것으로 검증했다.
- 이미지 준비 중 텍스트·이미지·FastAPI 중 하나가 종료되면 실패 경로로 들어가고, 두 모델이 준비된 뒤에는 기존처럼 두 SGLang 프로세스를 감시한다.
- 회귀 테스트 3종(기동 순서, 텍스트 조기 종료 시 이미지 미기동, 선택적 max-running-requests)과 VRAM 로그 검증을 추가했다. 기존 테스트를 유지했다.
- 검증 결과: `.venv/bin/python -m pytest -q` → `427 passed, 2 warnings in 20.22s`; `bash -n deploy/sglang/entrypoint.sh` → exit 0; `git diff --check` → 통과.
- 실제 Stage L40S/SGLang GPU 기동은 이 개발 환경에서 수행하지 않았다. 현재 작업 트리의 기존 미추적 파일 `docs/operations/infra-handoff-2026-09-23b.md`, `scripts/runtime/measure_vram.sh`는 변경하지 않았다.
