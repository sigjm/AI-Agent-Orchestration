# 사내 Ubuntu 서버에 Stage와 같은 FE-BE-AI를 띄워 실제 사이트로 전체 흐름 테스트 · 로그 수집

관리자(메인 Claude 세션) 지시다. 결과는 이 파일 하단 `## 결과`에 한국어로 쓰고, 로그·스크린샷은
`.orchestration/reports/20261001-ubuntu-e2e/`에 모은다.

## 왜

AWS Stage는 2026-10-01 19:20부터 노드 9대가 전부 배치 금지(unschedulable)라 FE-BE-AI를 확인할 수 없다.
같은 버전을 사내 Ubuntu 서버(`<ubuntu-server>`, x86_64 리눅스·GPU)에 띄워, 실제 브라우저로 사이트를 열고
판매자 → 상세페이지 생성 → 상품 화면, 구매자 → 챗봇 흐름이 끝까지 되는지 확인한다.

- 접속이 안 되면 **로컬 Mac으로 대신 진행하지 말고** 바로 멈춰서 `## 결과`에 "접속 불가"와 시도한 방법을 쓴다.
  어디서 돌릴지는 관리자가 정한다.

## 2. 실제 사이트 테스트 (브라우저 — Playwright 등으로 화면을 직접 조작)

FE를 브라우저로 열고 사람이 하듯 클릭·입력한다. 각 단계 스크린샷, 브라우저 콘솔, 네트워크(HAR 또는 요청·응답 상태 목록)를 남긴다.

1. **판매자: 상품 등록 → AI 상세페이지 생성**
   - 판매자(ARTISAN) 계정으로 로그인, 상품 등록
   - 사진: BE 저장소 `docs/demo-images`의 합죽선 사진 중 5장
   - 입력: 상품명 `전주 합죽선 · 매화선`
     - 제작 과정: `담양 왕대를 3년 건조해 손으로 겉대·속대를 깎고, 한지를 겹겹이 붙여 선면을 만들었습니다. 매화를 한 획씩 직접 그려 같은 부채가 하나도 없습니다.`
     - 관리 방법: `펼칠 때는 아래에서 위로 천천히 펴 주세요. 사용 후에는 접어 직사광선과 습기를 피해 보관하면 오래 쓸 수 있습니다. 물티슈·물세척은 한지가 상하니 피해 주세요.`
   - 초안 생성 → 승인 → 렌더 → BE 콜백까지 기다린다. 단계별 소요 시간을 잰다(BE 렌더 타임아웃 300초).
   - 상품 상세 화면에서 확인: 섹션 색(베이지 `#F6F2EC`가 아니라 디자인 토큰 색), **AI 생성 사진이 실제로 뜨는지**("이미지를 불러올 수 없습니다" 여부), 사진 생성 성공 여부.
2. **구매자: 챗봇**
   - 구매자(USER) 계정으로 로그인, 챗봇에서 4턴 이상 대화(상품 찾기 → 조건 좁히기 → 선물 추천 등). 턴별 응답 시간과 답변 내용을 기록한다.
3. **"다시 시도" 재현**
   - Stage에서 본 원인 가설: 액세스 토큰(30분)이 만료되면 `/api/chatbot/**`가 401이 아니라 **403**을 돌려주고, FE는 401일 때만 토큰을 갱신하므로 "일시적인 오류… 다시 시도" 배너가 뜨고 다시 눌러도 계속 실패한다.
   - BE `access-token-expiry`를 짧게(예: 2분) 해서 띄우고, 만료 뒤 챗봇 전송 → 응답 코드·FE 화면·다시 시도 결과를 확인한다. 가설이 틀리면 실제 원인을 쓴다.

## 3. 로그 수집

FE, BE, 상세페이지 AI(serve-ai·SGLang 텍스트·이미지 서버), 챗봇 API, 챗봇 LLM 로그를 테스트 시간 전체 구간으로 저장한다.
GPU 사용(`nvidia-smi` 주기 기록)과 컨테이너 메모리도 남긴다.

### 바뀐 결정
- SSH 접속 복구 완료: `ssh <user>@<ubuntu-server>` (Mac 키 등록됨, 계정은 `<user>`).
- **서버에 GPU가 없다** (i7-8565U·RAM 15GB·MX150 드라이버 없음). 관리자가 정한 구성:
  - **서버**: FE, BE, BE용 PostgreSQL·Redis, 이미지 저장소(MinIO), 챗봇 API(Stage ECR 이미지)와 벡터 DB
  - **Mac**(<mac-ip>, 64GB): 상세페이지 AI(우리 저장소 `deploy/ubuntu` = GenAI `c3f9f0e`, MLX Qwen3.8-27B + flux2-klein-9b-4bit), 챗봇 LLM(Ollama `gemma4:12b`)

1. 서버: `cd ~/midam-e2e && docker compose up -d db redis minio minio-init vectordb` → `docker compose up -d --build backend` (Gradle 빌드 몇 분) → `docker compose up -d frontend` (npm ci·build) → `docker compose up -d chatbot-api`. 각 로그로 기동 확인

3. Mac: `mlx-serve --serve --host 127.0.0.1 --port 11234 --model-dir ~/.mlx-serve/models --ctx-size 32768 ...`(오늘 쓴 옵션은 `be-repro-2/run30/mlx-serve.log` 참고) → 우리 저장소에서 `local.env` 기준 + `BACKEND_URL=http://<ubuntu-server>:18080`, `BACKEND_AUTH_TOKEN=<test-token>`, `AI_INTERNAL_AUTH_TOKEN=<test-token>`으로 `serve-ai`를 `127.0.0.1:8000`에 띄움. Mac 메모리 때문에 텍스트·이미지 모델 동시 적재가 어려우면 오늘 했던 것처럼 승인 전에 텍스트 모델을 내린다(그렇게 했으면 결과에 쓴다)

## 결과

### 실행 및 구성

- SSH <user>@<ubuntu-server> 접속 성공. 서버 ~/midam-e2e에 PostgreSQL, Redis, MinIO, 벡터 DB, BE, FE, 챗봇 API를 기동하고 FE는 http://<ubuntu-server>:13300에서 실제 Chrome/Playwright로 조작했다. Mac에서 서버 포트로 직접 연결되지 않아 브라우저는 SSH SOCKS 포워드(13301), AI 콜백은 SSH 로컬 포워드(18080), 서버→Mac AI/Ollama는 지정 역방향 포워드(18200/11434)를 사용했다. 경로 근거: ../reports/20261001-ubuntu-e2e/browser-access-route.txt.
- BE·FE는 관리자가 제공한 임시 소스 디렉터리에서 빌드했다. BE Gradle BUILD SUCCESSFUL in 36s, FE npm ci && npm run build는 정적 페이지 25/25 생성 및 Next 서버 Ready 확인. 임시 소스에 Git 메타데이터가 없어 BE b9e9bfc / FE 5ac78de가 정확히 일치하는지는 독립 검증할 수 없다. GenAI는 c3f9f0e를 확인했다. 챗봇 API는 지정 ECR 이미지 digest sha256:dc2328ba1494d89e80b07cf4846d4d908eb8de6f96336d449257d573efd75584를 유지했다.
- Mac 모델은 지정 Qwen ddalcu/Qwen3.8-27B-MLX-Serve-4bit, FLUX mlx-community/flux2-klein-9b-4bit, Ollama gemma4:12b를 사용했다. 모델을 교체하지 않았다. 챗봇 API 시작 시 지정 경로에 BGE-M3 임베딩 파일이 없어 공개 원본의 정확한 revision 5617a9f61b028005a4858fdac845db406aefb181을 받아 읽기 전용으로 마운트했다. MinIO 이미지 pull이 실패해 공식 RELEASE.2025-09-07T16-13-09Z를 임시 빌드했다.
- BE 테스트 설정은 만료 재현 때만 120초(보충 화면 재현은 20초)로 바꾸고 종료 후 기본 JWT_ACCESS_TOKEN_EXPIRY=1800000으로 복구했다. 최종 JOB_AI_BULK_SYNC_ENABLED=false. 테스트 전용 Compose override이며 Stage 리소스/비밀값은 사용하지 않았다.
- Git 상태를 바꾸는 명령은 실행하지 않았고 BE·FE·GenAI 소스도 수정하지 않았다. 요청된 이 작업 파일의 결과와 ../reports/20261001-ubuntu-e2e/ 증거 파일만 기록했다. 기존 서버 서비스는 건드리지 않았다.

### 오류 원인 및 담당

- 상세페이지 AI·콜백 (AI/BE 계약): SQLite outbox에서 복원한 기본 persist DTO가 별칭 필드를 잃어 BE가 요구하는 metadata.productId와 metadata.detailPage.reactDocument가 누락되고, BE AiCallbackController가 500을 반환했다. 정규 DTO 요청은 동일 생성 결과를 SAVED로 저장했다. 자동 콜백 직렬화와 BE 입력 계약을 맞춰야 한다.
- 상세페이지 사진 (BE 응답/FE 매핑): BE 콘텐츠 응답에 이미지 variant URL이 없어 FE ServerStudioEditor가 이미지를 찾지 못했다. 저장된 사진 객체와 상세페이지 응답의 이미지 매핑을 확인해야 한다.
- 초안 승인 (FE/BE 기능 연결): FE가 이 생성 작업의 초안 조회·승인 API가 연결되지 않았다고 표시했다. 이번 테스트에서 판매자 승인 단계는 검증되지 않았고 scheduler 자동 렌더가 대신 실행됐다.
- FLUX 503 (AI 런타임 메모리): Mac에서 Qwen 상주 16.95GB와 FLUX 필요 메모리가 동시에 맞지 않았다. 정확한 Qwen을 unload해 순차 실행한 뒤 FLUX 생성은 성공했다. 두 모델 동시 상주 가능 여부는 확인되지 않았다.
- 챗봇 카드 FE 실패 표시 (FE/BE 스키마): 챗봇 API 상품 카드의 reason이 null인데 FE 검증 스키마는 문자열을 요구한다. 응답 계약 또는 nullable 처리가 필요하다.
- 만료 후 “다시 시도” (BE 인증 응답/FE 갱신): 만료된 액세스 토큰에 BE가 401 대신 403을 주고 FE 갱신 경로는 401에만 반응한다. 재시도 시 새 세션 생성도 403을 받아 실패한다. 최초 가설을 실제 확인했다.
- 초기 챗봇 RAG 실패 (테스트 구성): API 시작 시 /models/bge-m3가 없어 FileNotFoundError가 발생했다. 정확한 BGE-M3를 읽기 전용 마운트한 뒤 모델 로드 완료와 브라우저 대화를 확인했다.
- 부수 로그: 상품 생성 이벤트의 FE 재검증 webhook은 BE webhookSecret=null로 NPE가 났다(테스트 BE 설정 누락). FE deprecated 패키지 경고, BE Hibernate dialect/PageImpl 경고가 있었으나 FE 구동 및 API 응답은 확인했다. 첫 BE 시작 시 AI 서비스 준비 전 상품 동기화 요청은 연결 실패했으나 AI 준비 뒤 재기동해 729개 동기화했다.

### 사용자 접근 권한 오류 재확인 (2026-10-02)

- 이전 장애와 같은 조건으로 Ubuntu 테스트 BE만 `JWT_ACCESS_TOKEN_EXPIRY=120000`을 임시 적용했다. 구매자 `e2e-user@midam.test` 브라우저 로그인 후 135초 대기하고 챗봇을 전송했다. 만료된 세션 생성 요청은 401, FE 토큰 갱신은 200, 새 세션 생성은 201, 답변 메시지는 201이었다. 403 응답·접근 거부 문구·재시도 배너는 없었고 브라우저 요청 실패도 없었다.
- 검증 직후 BE만 기본 `JWT_ACCESS_TOKEN_EXPIRY=1800000`으로 되돌려 재기동했다. FE·DB 및 나머지 컨테이너는 재기동하지 않았다. BE 헬스체크 200, FE 200, 공개 상품 API 7개를 확인했다. DB의 상품 수(ON_SALE 7 / HIDDEN 655 / DRAFT 70)와 상품 731·732 상태가 유지됐다. `ddl-auto=update`, `JOB_AI_BULK_SYNC_ENABLED=false`도 확인했다.
- 복구 후 새 브라우저에서 같은 구매자 계정으로 로그인·챗봇을 다시 실행해 로그인 200, 세션 201, 메시지 201을 확인했다. 챗봇에는 `접근 권한이 없어요.`가 나타나지 않았다. 같은 USER 계정으로 판매자 스튜디오에 진입하면 의도된 `판매자 계정이 필요합니다` 안내가 나온다. 판매자 작업에는 ARTISAN 계정을 써야 한다.
- 접근 거부 화면의 원인을 도메인에서 재현했다. Ubuntu Playwright에서 `https://<test-domain>/login`은 200으로 열리지만, 브라우저에서 `POST /api/member/login`을 호출하면 403 (`Server: cloudflare`)이다. 로그인 폼도 `접근 권한이 없어요.`를 표시한다. 같은 URL에 대한 서버 측 빈 요청은 Cloudflare Error 1010 `browser_signature_banned`로 응답하며, 상세 문구는 브라우저 서명/User-Agent 기준으로 사이트 소유자가 차단했다고 명시한다. FE의 `error-messages.ts`는 모든 403을 동일한 `접근 권한이 없어요.`로 표시해 Cloudflare 차단 원인을 계정 권한 오류처럼 보이게 한다.
- 이 문제는 USER 역할이나 비밀번호가 원인이 아니다. 구매자 계정은 Ubuntu 테스트 주소에서 로그인 200, 챗봇 세션·답변 201로 동작했고, FE·BE의 테스트 사본과 DB에는 추가 변경을 하지 않았다. 도메인 오류를 풀려면 `<test-domain>`의 Cloudflare 보안 설정에서 일치하는 Browser Integrity Check/User-Agent 차단 규칙을 소유자가 확인해 조정해야 한다. 이 세션에서는 Cloudflare 계정 관리 권한을 사용할 수 없어 보안 규칙은 바꾸지 않았다.
