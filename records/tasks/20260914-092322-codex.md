## 지시

Ubuntu 서버 배포용 컨테이너 이미지를 바로잡습니다. 관리자 지시: "Ubuntu 서버에 올릴 수 있게 브랜치 하나 파서 준비". 브랜치 `deploy/ubuntu` 가 이미 만들어져 체크아웃돼 있습니다. **이 브랜치에서만 작업하고, main 으로 옮기지 마세요.** 커밋도 하지 마세요.

## 담당 범위
`Dockerfile`, `.dockerignore`, 그리고 아래 3번 경로 문제를 막는 데 꼭 필요한 최소한의 코드. `docker-compose.yml`, `.env.example`, `docs/` 는 agy 가 동시에 씁니다 — 건드리지 마세요.

## 관리자가 확인한 배포 결함 (지금 Dockerfile 로 올리면 이렇게 깨집니다)
1. **rembg·onnxruntime 미설치.** Dockerfile 이 의존성을 손으로 적어 `pip install` 하는데 `pyproject.toml` 의 `onnxruntime==1.29.0`, `rembg==2.0.69` 가 빠져 있습니다. 누끼 첫 호출에서 import 오류.
   → 의존성 목록을 Dockerfile 에 복제하지 말고 **`uv.lock` 기준으로 설치**하세요(`uv sync --locked --no-dev` 등). 목록이 두 곳에 있어서 생긴 결함이므로 한 곳(잠금 파일)만 보게 만드는 것이 근본 수정입니다.
2. **렌더 템플릿·캡처 스크립트 경로.** `src/detail_page_ai/html_renderer.py:19` 는 `PROJECT_ROOT = Path(__file__).resolve().parents[2]` 로 `web/detail_page.html`, `web/detail_page.css`, `scripts/runtime/render_detail_page.mjs` 를 찾습니다. 지금 이미지는 `pip install --no-deps .` 로 패키지를 site-packages 에 복사하므로 `parents[2]` 가 `/usr/local/lib/python3.13` 쯤이 되고, 게다가 `web/` 은 복사조차 안 합니다.
3. **레이아웃 카탈로그 소리 없이 소실.** `src/detail_page_ai/layout_archetypes.py:15` 도 같은 `parents[2]` 로 `assets/references/detail-page-layouts.json` 을 찾는데, 파일이 없으면 오류 없이 빈 목록을 돌려줍니다(`load_layout_catalog`). 이미지에 이 파일이 없으면 레이아웃 다양화가 조용히 꺼집니다.
   → 2·3번은 **코드를 고치기보다 이미지 안에서 `/app` 소스 트리 구조를 유지해 `parents[2]` 가 `/app` 을 가리키게** 하는 쪽이 가장 작은 수정입니다(예: uv 가 프로젝트를 편집 가능 모드로 설치하거나 `PYTHONPATH=/app/src` 로 소스에서 실행). 그리고 `web/`, `assets/references/`, `scripts/runtime/render_detail_page.mjs` 를 복사하세요. 코드 수정이 불가피하면 이유를 보고하세요.
4. **rembg 모델 재다운로드.** birefnet-general 모델(973MB)이 첫 누끼 때 `~/.u2net` 에 받아집니다. 컨테이너를 새로 띄울 때마다 다시 받지 않도록 `U2NET_HOME=/var/lib/detail-page-ai/models/u2net` 으로 지정해 기존 볼륨 `/var/lib/detail-page-ai` 안에 두세요. appuser 가 쓸 수 있어야 합니다.

## 결과

### 변경 파일

- `Dockerfile`만 변경했습니다. `.dockerignore`는 필요한 `web/`, `assets/references/detail-page-layouts.json`, `scripts/runtime/render_detail_page.mjs`, `uv.lock`을 이미 제외하지 않아 수정하지 않았습니다. 애플리케이션 코드는 변경하지 않았습니다.
- 수동 `pip install` 목록을 제거하고 `ghcr.io/astral-sh/uv:0.11.4`에서 가져온 `uv`로 `uv sync --locked --no-dev --no-install-project --no-cache`를 실행하게 했습니다. 이 저장소는 빌드 시스템을 선언하지 않아 프로젝트 자체 설치가 불가능하므로, 잠금된 런타임 의존성만 설치하고 아래 소스 실행 방식을 사용했습니다.
- `PYTHONPATH=/app/src`와 가상환경의 `serve-ai` 래퍼를 추가해 `/app/src`의 소스를 실행합니다. 따라서 `html_renderer.PROJECT_ROOT`가 `/app`이고, `web/`, `assets/references/detail-page-layouts.json`, `scripts/runtime/render_detail_page.mjs`를 이미지에 명시적으로 복사해 코드가 계산하는 경로에서 찾습니다.
- `U2NET_HOME=/var/lib/detail-page-ai/models/u2net`을 설정하고 해당 디렉터리를 생성해 기존 볼륨(`/var/lib/detail-page-ai`) 아래에서 appuser가 쓸 수 있게 했습니다.
- 기존 Dockerfile의 `HEALTHCHECK ... CMD-SHELL`은 Dockerfile 파서에서 `Unknown type "CMD-SHELL"`로 빌드 자체가 실패했습니다. 동일한 Python HTTP 404 확인 로직을 JSON `CMD` 형식으로 바꿔, 헬스체크 방식과 검사 대상은 유지하면서 Docker 빌드 문법만 바로잡았습니다.

### 검증

- 브랜치: `deploy/ubuntu`.
- `docker buildx build --platform linux/arm64 -t detail-page-ai:ubuntu-check-arm64 --load --progress=plain .` 성공. ARM64 컨테이너에서 `rembg 2.0.69`, `onnxruntime 1.29.0` import 성공, `PROJECT_ROOT=/app`, `/app/web/detail_page.html`, `/app/web/detail_page.css`, `/app/scripts/runtime/render_detail_page.mjs`, `/app/assets/references/detail-page-layouts.json` 존재를 확인했습니다. `load_layout_catalog()`은 25개 항목을 반환했고 `U2NET_HOME=/var/lib/detail-page-ai/models/u2net`은 appuser 쓰기 가능했습니다.
- ARM64 이미지의 기본 명령(`serve-ai`)을 볼륨과 함께 실행해 세 번째 확인에서 Docker HEALTHCHECK가 `healthy`가 됐습니다. 컨테이너와 검증용 볼륨은 제거했습니다.

- 호스트 검증: `.venv/bin/python -m pytest -q` → `349 passed in 10.93s`.
